01The problem & the three ideas

Localisation teams structure scripts as books → episodes → script rows. One show can reach a million rows needing translation into many languages. Machine translation is cheap per call and ruinous at that volume, and raw output destroys exactly what a script depends on: character names, placeholders, sound cues, line breaks, numbering.

IdeaWhy it carries the design
Rules enforced structurally Sarvam's /translate is pure text-in/text-out with no system prompt, so "preserve placeholders, keep line breaks, never summarise" cannot be asked for. Each rule is guaranteed by controlling what the model physically sees — then verifying the output. Unverifiable rows are parked, never shipped.
The queue is Postgres No Redis, no broker. SELECT … FOR UPDATE SKIP LOCKED gives safe multi-worker claiming; jobs stay transactionally consistent with the data they touch; progress rides Supabase Realtime with no third moving part.
Review compounds A human correction updates the row and writes to translation memory as origin='human'. A SQL-level guard stops machine output ever overwriting it, so review effort accumulates permanently.
Measured on a real 500-row episode

Hindi → Tamil completed in ~12 seconds, zero failures, 8 Sarvam API calls — 64% cache hit on a cold start. Placeholders, stage cues and character names all intact.

Scope, stated honestly

Sarvam covers English and the 22 scheduled Indian languages and nothing else — Spanish, Japanese, Chinese and similar are unreachable through this provider. I verified that against the API docs before writing code and raised it, rather than shipping a dropdown full of languages that fail at runtime. The supported set lives in one file; the provider abstraction exists so a second provider can widen it in one more.

02Architecture

Pressing Translate does not translate. It enqueues and returns 202 Accepted in milliseconds — a 5,000-row episode would outlive any HTTP timeout. A background worker does the work.

One broadcast per slice

mark_job_items() settles a slice and recomputes counters in one transaction — a single UPDATE carrying a consistent snapshot. Five events for a 500-row job, not 500, and no torn intermediate state.

Framework-free core

Nothing in services/translation/ imports Next.js; the database is reached through a MemoryPort interface. That is why the whole pipeline unit-tests against an in-memory fake with no database — 44 tests in under a second.

03Data model & the decisions worth defending

organizations ─┬─ org_members ── profiles ── auth.users
               └─ books ── episodes ── script_rows ── translations
                                                      UNIQUE(script_row_id, target_language)
   translation_jobs ── translation_job_items          translation_memory (hash-keyed)
DecisionReason
bigint identity for script_rows, not uuid The million-row table, always read in row_index order and referenced by every translation row. 8 bytes and sequential vs 16 and random — inserts append to the right edge of the B-tree instead of scattering across it.
org_id denormalised onto every table RLS evaluates on every row of every query. Deriving org through a two-level join would make the policy dominate the plan; storing it makes each check one indexed lookup.
Partial indexes The claim query only sees status='queued', so that index stays small as millions of finished rows accumulate. A unique partial index on (episode_id, target_language) where status in ('queued','running') makes duplicate live jobs impossible — a correctness constraint, not an optimisation.
Trigram GIN for search Makes ILIKE '%q%' index-backed. A B-tree can't serve a leading wildcard; tsvector does stemmed whole-word matching — wrong for finding a partial character name.
Keyset pagination, never OFFSET OFFSET 900000 reads 900,100 rows to return 100. WHERE id > ? reads 100 at any depth, and is stable under concurrent inserts.

Status model: pending → machine → edited → approved, plus failed. The bulk writeback only touches ('pending','failed','machine'), so a reviewer editing a row mid-job can never be overwritten by machine output landing a second later.

04The translation pipeline

The hardest engineering in the project — and the part that stops it looking generic.

RuleHow it is guaranteed
Character names preservedSpeaker prefix split off and reattached; only dialogue is sent.
Placeholders preserved{x}, {{x}}, %s, <b>, [SFX: …], ${x} masked to sentinels, restored after, and verified.
Line breaks preservedEach line translated separately, rejoined with its original separator.
Numbering preservedLeading 1., 1), -, • never enter the payload.
No summarisingThe model sees one line at a time — there is nothing to summarise.
translateLine(line)
  ├─ protect(line, style)     MASK FIRST — the order is load-bearing
  ├─ splitLine(masked)        → { marker, speaker, body, trailing }
  ├─ hasTranslatableContent() no letters? return free, 0 API calls
  ├─ chunkText(body, 2000)    sentence-aware, danda-aware (। ॥)
  ├─ provider.translate()     per chunk, bounded concurrency
  ├─ joinLine() + missingTokens()   VERIFY every sentinel came back
  │    └─ missing? retry with a different sentinel shape
  │       └─ still missing? THROW — park the row, never ship it
  └─ restore()
Masking must precede speaker splitting

[SFX: door creaks] contains a colon. Split first and [SFX looks like a speaker, so door creaks] gets translated — producing [SFX: கதவு கீச்சிடுகிறது. with the bracket destroyed. Mask first and the cue is one opaque token. This was a real bug, caught only against the live API.

Failing loudly is the deliberate choice. A flagged row is visible and fixable in the review queue; silent corruption across a million rows might not surface until it reaches a dubbing studio. Correctness beat completeness because the failure mode was silent and the blast radius large.

Cost control — four layers, in order

1. Skip untranslatable rowsNo letters (..., ---, 42) → zero calls.
2. In-slice deduplicationIdentical rows collapse to one call even on a cold cache.
3. Translation memoryEvery line hashed (SHA-256 over NFC-normalised text) and looked up first.
4. Corrections persistWHERE origin='machine' OR excluded.origin='human' — enforced in SQL, so no code path can violate it.

The hash is computed in the app, not as a generated column, deliberately: two implementations of the same normalisation would drift and silently split the cache in two — a failure that costs money while erroring nowhere.

05Reliability & security

Four failure modes

429 / 5xx / timeoutRetry with exponential backoff + full jitter, honouring Retry-After.
Row keeps failingRequeue to maxAttempts, then park as failed for a human.
Worker diesrequeue_stuck_job_items() reclaims items locked >10 min.
4xxNever retried — malformed stays malformed; retrying burns quota.

Full jitter, not plain backoff: every worker trips a rate limit at the same instant, and identical sleeps would reconverge them onto the same wall.

Security model

Tenant isolationRLS on all 10 tables. Authorisation is in the database — a forgotten WHERE in a route still returns nothing.
Rolesowner / editor / reviewer / viewer. Reviewers correct translations but cannot alter source.
No RLS recursionSECURITY DEFINER helpers, always with set search_path = public — omitting it is a real privilege-escalation vector.
SecretsServer-only, Zod-validated at boot, guarded against browser import. Service role is worker-only.

Verified three ways

44 unit testsFake provider. Placeholder round-trip, speaker splitting, chunking, routing, dedup, failure isolation.
12-step SQL smoke testReal Postgres 18 cluster with Supabase objects stubbed. Caught two migration bugs review would not have.
Live API checknpm run check:sarvam — the only layer that catches a rule surviving a fake but not reality.

The most valuable tests are the negative ones: machine cannot overwrite human; a viewer cannot start a job. Those prove a guarantee rather than a behaviour.

06Three bugs worth telling

Interviewers use debugging stories to separate builders from tutorial-followers.

1 · The stage cue that got translated

Symptom: [SFX: door creaks] returned translated, closing bracket gone — while every unit test passed. Why tests missed it: the fake provider echoed text back, so a structural mistake was invisible. Root cause: speaker-splitting ran before masking; the colon in the cue made [SFX match the speaker pattern. Neither function was wrong alone — the ordering was. Fix: mask first, then split; plus a rule that names never contain brackets. Regression tests at both layers; sample-set API calls also fell 6 → 4.

Lesson: mocks verify the contract you imagined; only the real dependency verifies the one that exists.

2 · interface vs type collapsing every query to never

~60 type errors, all "Property 'title' does not exist on type 'never'". Supabase's GenericSchema requires Row extends Record<string, unknown>, and TypeScript interface declarations don't get an implicit index signature — type aliases do. The schema silently failed the constraint. Diagnosed by writing a one-line probe asserting Database["public"] extends GenericSchema rather than guessing across 60 errors. Converting 14 shapes took errors 60 → 6.

3 · The dead Translate button

Report: "translation is not working." Investigation: checked the data before touching code — the job had completed, 500/500, zero failures, correct text present. Root cause: the page defaults to English for a Hindi source book, English was already fully translated, so pendingRows === 0 rendered a greyed-out "Translate 0 rows". A finished episode looked identical to a broken one. Fixed by making the state legible: "Re-translate 500 rows" plus an "All 500 rows translated" badge.

Lesson: "not working" is a symptom, not a diagnosis — and a disabled control with no explanation is indistinguishable from a broken one.

Also worth a sentence each

A Postgres function inserting two columns from a one-column SELECT, and an untyped CASE needing ::job_status — both caught by applying migrations to a real database, not by review. And REPLICA IDENTITY FULL: Realtime on an RLS table filtered by a non-key column silently delivers nothing, because the default identity writes only the primary key to the WAL. No error, just a progress bar frozen at 0%.

07Limitations & what's next

Known limits

  • 23 languages — a provider constraint, not architectural.
  • Single-org UI; the schema already supports more.
  • No glossary / term base — the clearest gap for real teams.
  • Row-level TM only; segment-level would raise hit rates.
  • DB types hand-maintained, should be generated in CI.
  • No rate limiting or audit log yet.

Roadmap, in order

  1. Glossary — enforced terminology, reusing the masking machinery.
  2. Second provider — unlocks non-Indic languages.
  3. Segment-level memory — higher hit rate, lower cost.
  4. Quality signals — length ratio, script detection.
  5. Import/export — CSV, SRT, FDX.
  6. Partitioning by book_id near 50M rows.

0824 interview questions

Condensed answers. Lead with the decision, then the reason.

Architecture · design decisions and trade-offs
Q1
Describe the project in 60 seconds.

A localisation platform for comic and dubbing scripts — books → episodes → rows, up to a million rows per show. Press Translate and it enqueues, because that volume outlives any request timeout. A worker claims slices with SKIP LOCKED, checks translation memory, sends only genuinely new lines to Sarvam with bounded concurrency, writes back in one set-based statement, and streams progress over Realtime. The hard part was quality: the API has no system prompt, so rules like "preserve placeholders" are enforced structurally and verified, not asked for. Result: 500 rows for 8 API calls, zero failures.

Q2
Why not translate synchronously?

Thousands of rows × a few hundred ms each exceeds any HTTP or serverless timeout. Async also buys resumability (a crash loses one slice, not the job), horizontal scale, and visible progress. The endpoint returns 202 Accepted — the honest code for accepted-but-not-done.

Q3
Why a Postgres queue rather than Redis or SQS?

Transactional consistency — job state and translated rows are in one database, so settling a slice is atomic; with an external broker a crash between "acked" and "written" leaves them permanently disagreeing. SKIP LOCKED is genuinely sufficient for safe multi-consumer claiming. No second system to deploy, secure and monitor. I'd switch at tens of thousands of jobs/sec, where queue traffic competes with application queries — or if I needed fan-out to independent consumer groups.

Q4
How would you add a second provider?

One class implementing TranslationProvider — name, model, maxInputChars, supports(), translate() — plus one line in the registry. Registration order is preference order, so Sarvam keeps Indic pairs and others fall through. maxInputChars makes chunking adapt automatically; supports() rejects an unsupported pair up front instead of via a 400 mid-batch.

Q5
Where does business logic live — app or database?

The test is: could a future code path violate this? If yes, it belongs in the database. So invariants are SQL — org scoping via RLS, one live job per episode/language via a partial unique index, machine-never-overwrites-human via a guarded upsert. Rich logic and external calls stay in the app: text protection, chunking, routing, retry policy. Invariants in application code are conventions; in the database they're guarantees.

Database · Postgres, indexing, RLS
Q6
Explain FOR UPDATE SKIP LOCKED.

FOR UPDATE takes a row lock; normally a second transaction blocks on it. SKIP LOCKED skips locked rows instead. So ten workers each asking for 100 queued items get disjoint sets with no waiting. Without it they'd all target the same rows in id order and serialise into a single-consumer queue with extra steps.

Q7
Why bigint for script rows but uuid for books?

Access pattern and volume. Script rows are the million-row table, read in order and referenced by every translation row: 8 bytes sequential beats 16 bytes random, and sequential keys append to the right edge of the B-tree instead of scattering writes. Books are few and their ids appear in URLs, where uuids avoid leaking counts or allowing enumeration. UUIDv7 would give both if I wanted one scheme.

Q8
Keyset vs OFFSET pagination?

OFFSET reads and discards everything it skips — page 9,000 reads 900,100 rows to return 100, degrading linearly. Keyset (WHERE id > ?) seeks into the index and reads 100 at any depth. It's also stable under concurrent inserts, where OFFSET can repeat or skip rows. Cost: no random access to page N — irrelevant here.

Q9
How does RLS avoid infinite recursion?

The policy on org_members needs to query org_members, which re-triggers the policy. SECURITY DEFINER helpers run as owner and bypass RLS for that lookup. They must also set search_path = public — otherwise a caller could shadow org_members with their own table in an earlier schema and hijack the elevated privilege. That's a documented Postgres escalation vector, not theoretical.

Q10
What's a partial index and why here?

An index with a WHERE clause, containing only matching rows. The claim query only sees status='queued', so the index stays small and cache-resident however much history accumulates. The second one is a correctness constraint: a unique partial index makes duplicate live jobs impossible even under a race.

Q11
How do you write 100 results efficiently?

One UPDATE … FROM jsonb_to_recordset(p_results). The worker sends the slice as JSON, Postgres expands it to a relation, the update joins against it. A hundred single-row updates would be a hundred round trips — at a million rows, the difference between minutes and hours. The same statement carries the status guard protecting human edits.

Q12
What is REPLICA IDENTITY FULL?

It controls how much of the old row goes into the WAL on UPDATE. The default writes only the primary key — which broke Realtime here, because the subscription filters on episode_id (not the PK) and the table is RLS-protected, so Realtime needs the full row to evaluate visibility. Symptom: no error anywhere, just a progress bar frozen at 0% while the job completed. Cost of the fix is a larger WAL record per update — negligible, since the table updates once per slice.

Queue, APIs & resilience
Q13
Two users click Translate at once — what happens?

One job. The function first returns any live job for that pair; if both pass that check simultaneously, the partial unique index makes the second insert fail. The check handles the common case efficiently, the index handles the race correctly — relying on the check alone would be a TOCTOU bug.

Q14
Why bounded concurrency, not Promise.all?

Promise.all over a 100-row slice fires 100 simultaneous requests, immediately tripping rate limits — and rate-limit responses cost money in retries while achieving nothing. mapWithConcurrency keeps N in flight over a shared cursor, preserving input order. N is an env var because the right value is whatever the provider's limit allows.

Q15
Explain your retry strategy.

Retryability is a property of the error, not the operation. 429/5xx/timeouts are transient → exponential backoff with full jitter, honouring Retry-After. 4xx is never retried — it will stay malformed. That's why TranslationError carries a retryable flag: the decision is made where the error is understood. Above that, a row that keeps failing is requeued to maxAttempts, then parked for a human.

Q16
Why full jitter?

With plain backoff, every client that failed together waits the same interval and retries in the same instant — the herd re-forms each attempt. Full jitter picks uniformly between 0 and the ceiling, spreading them out. With 8 workers hitting one rate limit, that's a smooth recovery versus eight synchronised waves.

Q17
Why recompute counters instead of incrementing?

Incrementing is order-dependent and drifts — a retried slice or a double-settle after a crash produces a wrong total that never self-corrects. Recomputing with COUNT(*) FILTER (WHERE …) is idempotent: it derives truth from the queue's actual state, so running twice gives the same answer and drift heals on the next slice.

Q18
How do you test code that calls a paid API?

Three layers. Unit tests with a fake provider — fast and free. An injected fetch, so request shape, retries, 429 handling and error mapping are tested against stubbed HTTP with no network. And a deliberate live check, not in CI. That third layer earned its place: it caught the stage-cue bug the other two passed, because the fake echoed text back and the structural mistake was invisible.

Q19
The model is non-deterministic. How do you build reliably?

Verify rather than trust. Placeholders are checked on return; a missing sentinel triggers a retry with a different shape, and only then is the row parked. I measured this rather than assuming — probed eight sentinel shapes across four languages and confirmed #0# was fine, so the variance was model non-determinism, not a bad choice. The two-shape retry converts a random failure into a second attempt.

Domain, frontend & behavioural
Q20
Why not just prompt an LLM with the rules?

Sarvam's endpoint has no system prompt — there's no channel to send instructions through. But it's better anyway: a prompt is a request the model may ignore on long or unusual input; masking is a guarantee, because the protected content is physically absent from what the model sees. If I added an LLM provider I'd prompt as well, but keep the structural layer underneath — it's the one that can be verified.

Q21
How does the review loop improve quality over time?

An edit updates the row and writes the corrected wording into translation memory as origin='human', in one transaction. The next occurrence of that source line anywhere in the catalogue reuses it instead of re-asking the model — and since SQL blocks machine output from overwriting human entries, the improvement is permanent. That's the difference between a translation tool and a translation system.

Q22
Server vs Client Components — how did you decide?

Default to server; opt into client only where interactivity demands it. Pages are Server Components querying Supabase directly — no API layer, no loading state. Four leaf components are client-side: the translate panel (Realtime + fetch), the review table (inline editing), search, and forms. Keeping them leaves keeps shipped JS small. Middleware is load-bearing rather than decorative: Server Components can't set cookies, so without it refreshed sessions would silently expire.

Q23
Tell me about a difficult bug.

S: A stage cue came back translated with its bracket destroyed, while every unit test passed. I: The fake provider echoed text back, so the structural error was invisible; tracing the actual payload showed door creaks] being sent, not the whole cue. R: Speaker-splitting ran before masking, and the colon in the cue matched the speaker pattern — neither function wrong alone, the ordering was. A: Mask first, then split; regression tests at both layers; API calls also dropped 6 → 4. Lesson: mocks verify the contract you imagined, not the one that exists.

Q24
Tell me about a mistake you made.

I shipped a Translate button that rendered greyed-out as "Translate 0 rows" whenever an episode was already fully translated — no explanation, no way to re-run. A user reported "translation is not working," and they were right. The backend was healthy; I'd simply never designed a state for "already done", so success and failure looked identical. I'd validated the pipeline exhaustively and under-tested the interface around it. Now I treat empty and completed states as first-class rather than afterthoughts.
