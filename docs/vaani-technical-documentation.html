01Executive Summary

The problem, the solution, and the three ideas that make it work.

The problem

Localisation teams working on comics, animation and dubbing handle scripts structured as books → episodes → script rows. A single show can run to a million rows of dialogue, each needing translation into many languages. Machine translation is cheap per call but ruinous at that volume if applied naively, and raw MT output routinely destroys the things a script depends on: character names, placeholders, sound cues, line breaks and numbering.

The solution

Vaani is a multi-tenant web application that treats translation as a pipeline rather than an API call. Users import scripts, press Translate, and watch progress stream in live while a background worker drains a Postgres-backed queue. Every translation is cached; every human correction is fed back into that cache so the same mistake is never paid for twice.

Three ideas that carry the design

Idea Why it matters
Structural rule enforcement Sarvam's /translate is a pure text-in/text-out endpoint with no system prompt, so "preserve placeholders, keep line breaks, never summarise" cannot be asked for. Every rule is instead guaranteed by construction — the model physically never sees the protected content. Placeholders are masked to sentinels and verified on the way back; if verification fails the row is parked rather than shipped.
The queue lives in Postgres No Redis, no RabbitMQ, no second broker to run and monitor. SELECT … FOR UPDATE SKIP LOCKED gives safe multi-worker claiming for free, jobs are already in the database beside the data they operate on, and progress rides Supabase Realtime to the browser without a third moving part.
Review compounds A human correction updates the row and writes back to translation memory with origin = 'human'. A database-level guard prevents machine output from ever overwriting a human entry, so review effort accumulates permanently instead of being undone by the next run.

Measured result

Verified on a real 500-row episode

A Hindi → Tamil job over 500 script rows completed in roughly 12 seconds with zero failures and 8 Sarvam API calls — a 64% cache hit rate on a cold start, achieved through in-batch deduplication plus translation memory. Placeholders, stage cues and character names all survived intact.

Honest scope note

Sarvam's translate endpoint covers English and the 22 scheduled Indian languages and nothing else. Spanish, French, Japanese, Chinese and similar are unreachable through this provider. Rather than list languages the product cannot deliver, the supported set is defined in exactly one file (languages.ts) and the UI only ever offers what genuinely works. The provider abstraction exists precisely so a second provider can widen this later — that is a one-file change, not a refactor.

Interviewers rarely ask what you used. They ask why.

A stack question you should expect

"Why not Prisma / Drizzle / an ORM?" — The heavy lifting is set-based: claim 100 rows with SKIP LOCKED, write 100 results in one UPDATE … FROM jsonb_to_recordset, roll up counters in the same transaction. Those are expressed naturally in SQL and awkwardly through an ORM. The logic lives in Postgres functions, and TypeScript calls them as typed RPCs — which keeps the round trips down and the type safety up.

03System Architecture

What happens between pressing Translate and seeing Tamil on screen.

The critical insight: Translate does not translate

Pressing the button enqueues. A 5,000-row episode would blow through any HTTP request timeout long before it finished, so the request returns 202 Accepted in milliseconds and a background worker does the work. 

BROWSER                    NEXT.JS                      POSTGRES                 SARVAM

[Translate] ──POST────► /api/translate
                          │ auth: getUser()
                          └──RPC──────────────► enqueue_translation_job()

                                                  ├ create job
                                                  └ create N queue items
            ◄──202 { jobId }──┘

                        ── worker process (npm run worker) ──

                        runWorkerTick()

                          ├──RPC──────────────► next_runnable_job()
                          └──RPC──────────────► claim_job_items(limit 100)
                                                  FOR UPDATE SKIP LOCKED
                          │
                          ├ dedupe identical rows in slice
                          ├──RPC──────────────► translation_memory lookup
                          ├─────────────────────────────────────────────► POST /translate
                          │                                                (concurrency 8)
                          ├──RPC──────────────► apply_translation_results()
                          │                       one set-based UPDATE

                                                        │

                       postgres_changes on translation_jobs

Why progress is one broadcast per slice, not per row

mark_job_items() settles a whole slice and recomputes the job counters in the same transaction. That produces exactly one UPDATE on translation_jobs, carrying a consistent snapshot. Realtime pushes that single event to every subscriber. Updating per row would mean 500 broadcasts for one episode and a torn view of progress in between.

Two ways to run the worker

ModeWhen to use it
npm run worker
long-lived process		 Preferred for throughput. Pays connection setup once and drains continuously. Run several in parallel — SKIP LOCKED guarantees they take disjoint slices.
POST /api/worker/tick
HTTP, cron-driven		 For serverless deployments (Vercel Cron, pg_cron, GitHub Actions). Bounded to 3 slices per tick so it returns inside the platform's function timeout; the remainder is picked up next tick. Guarded by a shared secret, not a user session.

Design principle worth stating in an interview

Everything under services/translation/ is framework-free. It imports no Next.js, and the database is reached through a MemoryPort interface rather than a Supabase client. That is why the entire pipeline can be unit-tested with an in-memory fake and no database — and why swapping the web framework would not touch the domain logic.

Core tables

TableKey typePurpose & notable decision

org_memberscompositeRole per user per org: owner / editor / reviewer / viewer.

Four decisions worth defending

1. bigint identity for script_rows, not uuid

Rows are always read in row_index order within an episode, and every row is referenced by a foreign key from translations. A uuid is 16 bytes and random; a bigint is 8 bytes and sequential. At a million rows across several target languages this keeps the hot B-tree compact and the inserts append-only rather than scattered across the index.

2. org_id denormalised onto every table

It could be derived by joining script_rows → episodes → books. It is stored directly instead, because every RLS policy evaluates on every row read. Making that a single indexed lookup rather than a two-level join is the difference between an RLS predicate that is free and one that dominates the query plan.

3. Partial indexes on hot, selective predicates

-- The claim query only ever looks at queued work, so the index stays
-- small even when millions of finished items sit in the table.
create index translation_job_items_claimable_idx
  on translation_job_items (job_id, id)
  where status = 'queued';

-- Only one live job per (episode, language). A second Translate click
-- resumes the existing job instead of double-spending on the API.
create unique index translation_jobs_active_idx
  on translation_jobs (episode_id, target_language)
  where status in ('queued', 'running');

That second index is not an optimisation — it is a correctness constraint enforced by the database. Concurrency bugs in application code cannot produce a duplicate live job.

4. Trigram GIN indexes for search

create extension pg_trgm;
create index script_rows_text_trgm_idx
  on script_rows using gin (source_text gin_trgm_ops);

This makes ILIKE '%query%' index-backed. A B-tree cannot serve a leading wildcard, and full-text search (tsvector) does stemmed word matching rather than substring matching — wrong for finding a partial character name or a fragment of dialogue.

Status model

StatusMeaning
pendingRow exists, nothing translated yet.
machineMachine output, untouched by a human.
editedA human changed the machine output.
approvedA reviewer signed it off.
failedRetries exhausted; needs manual attention.

The distinction matters: apply_translation_results() only writes to rows in ('pending','failed','machine'), so a reviewer editing a row mid-job can never be overwritten by the machine output arriving a second later.

05The Translation Pipeline

The hardest engineering in the project, and the richest interview material.

The constraint that shapes everything

An LLM chat endpoint lets you ask for behaviour: "preserve placeholders, keep the line breaks, do not summarise." Sarvam's /translate is a pure text-in/text-out endpoint. There is no system prompt. Asking is not available.

So every rule is enforced structurally — by controlling what the model is physically shown:

RuleHow it is guaranteed
Character names preservedSpeaker prefix is split off and reattached; only the dialogue is sent.
Placeholders preserved{x}, {{x}}, %s, <b>, [SFX: …], ${x} masked to sentinels, restored after, and verified.
Line breaks preservedEach line translated separately, rejoined with its original separator (\n, \r\n, \r).
Numbering preservedLeading 1., 1), -, *, • markers never enter the payload.
Punctuation & spacingLeading/trailing whitespace split off and reattached verbatim.
No summarisingThe model only ever sees one line at a time — there is nothing to summarise.

The pipeline, step by step

translateText(text)
  └─ splitLines()                    keep exact separators
     └─ for each line: translateLine()
        ├─ protect(line, style)      MASK FIRST — order is load-bearing
        ├─ splitLine(masked)         → { marker, speaker, body, trailing }
        ├─ hasTranslatableContent()  no letters? return free, 0 API calls
        ├─ chunkText(body, 2000)     sentence-boundary aware, danda-aware
        ├─ provider.translate()      per chunk
        ├─ joinLine(parts, body)     reattach marker + speaker + whitespace
        ├─ missingTokens()           VERIFY every sentinel came back
        │    └─ missing? retry with a different sentinel shape
        │       └─ still missing? THROW — park the row, never ship it
        └─ restore()                 put the real placeholders back
Masking must happen before speaker splitting

A stage cue like [SFX: door creaks] contains a colon. Splitting first makes [SFX look like a speaker name and sends door creaks] off to be translated — producing [SFX: கதவு கீச்சிடுகிறது. with the bracket destroyed. Masking first turns the whole cue into one opaque token, so there is no colon left to trip on. This was a real bug, caught by testing against the live API. See Section 11.

Verification, and why failing loudly is correct

After translation the pipeline checks that every sentinel came back. If not, it retries with a different sentinel shape. If that also fails, it throws rather than returning text with mangled markup: 

throw new TranslationError(
  `Placeholders did not survive translation (${lastMissing.join(", ")}). ` +
    `Row parked for manual localisation rather than shipping broken markup.`,
  { retryable: false },
);

A flagged row is recoverable — it appears in the review queue with the error attached. Silent corruption spread across a million-row script is not. This is a deliberate trade of availability for correctness, and it is exactly the kind of judgement interviewers probe for.

Empirically choosing a sentinel

The sentinel shape is not a guess. Eight candidates were tested against the live API across four target languages:

SentinelSurvivalVerdict
#0#3 / 3 valid pairschosen — primary
((0))3 / 3chosen — fallback
[[0]], @0@, __0__, {0}, XX0XX3 / 3viable
<0>2 / 3 — Tamil dropped the >rejected

Two shapes are kept because the model is non-deterministic: the same input occasionally loses a sentinel that survived a moment earlier. The two-shape retry converts a random failure into a second attempt rather than a parked row.

The provider abstraction

export interface TranslationProvider {
  readonly name: string;
  readonly model: string;
  readonly maxInputChars: number;
  supports(source: LanguageCode, target: LanguageCode): boolean;
  translate(request: ProviderRequest): Promise<ProviderResult>;
}

maxInputChars lets the caller chunk correctly per provider without hardcoding any provider's limit (Sarvam: 2,000 chars for sarvam-translate:v1, 1,000 for mayura:v1). supports() lets the router skip a provider that cannot serve a language pair instead of discovering it through a 400. Adding Gemini or OpenAI is one new class plus one line in the registry — registration order is preference order.

06Job Queue & Concurrency

Why Postgres is a legitimate queue, and how failure is handled.

The claim, in full

with claimed as (
  select i.id
  from translation_job_items i
  where i.job_id = p_job_id
    and i.status = 'queued'
  order by i.id
  limit p_limit
  for update skip locked          -- ← the whole trick
),
locked as (
  update translation_job_items i
  set status = 'running',
      attempts = i.attempts + 1,
      locked_at = now(),
      locked_by = p_worker
  from claimed c
  where i.id = c.id
  returning i.script_row_id, i.attempts
)
select sr.id, sr.row_index, sr.character_name, sr.source_text, sr.notes, l.attempts
from locked l
join script_rows sr on sr.id = l.script_row_id
order by sr.row_index;

FOR UPDATE SKIP LOCKED tells Postgres: lock these rows, and if another transaction already holds a lock on one, skip it rather than waiting. Each worker therefore takes a disjoint slice and never blocks on another worker. Without SKIP LOCKED, ten workers would serialise behind one another on the same rows — the classic naive-queue failure.

Four failure modes, four answers

FailureHandling
Transient API error
429, 5xx, timeout		 Retried inside the provider with exponential backoff and full jitter, honouring Retry-After.
Row keeps failing Requeued until TRANSLATION_MAX_ATTEMPTS, then parked as failed with the error visible in the review table.
Worker dies mid-slice Items stay running forever. requeue_stuck_job_items() reclaims anything locked more than 10 minutes on the next tick.
Permanent error
400, bad key, unsupported pair		 Never retried. The whole slice is returned to the queue and the job fails loudly rather than grinding through 500 rows to reach the same conclusion.

Why full jitter

const ceiling = Math.min(maxDelayMs, baseDelayMs * 2 ** (attempt - 1));
const delay = retryAfterMs?.(error) ?? Math.random() * ceiling;

Random between zero and the computed ceiling, not the ceiling itself. When a rate limit trips, every in-flight worker sees it at the same instant; identical sleeps would reconverge them onto the same wall. Jitter spreads the retries out.

Idempotency

enqueue_translation_job() is idempotent. Clicking Translate twice returns the existing job rather than creating a second one — enforced both by an explicit check and by the partial unique index, so it holds even under a race.

07Translation Memory & Cost Optimisation

The commercial argument for the whole design.

Four layers, in the order they apply

#LayerEffect
1Skip untranslatable rowsLines with no letters (..., ---, 42, bare placeholders) return unchanged for zero calls.
2In-slice deduplicationIdentical rows in one slice collapse to a single call even on a completely cold cache.
3Translation memoryEvery source line hashed and looked up first. Catchphrases, SFX, intros and re-cut dialogue paid for once.
4Human corrections persistReviewed wording is reused forever and protected from machine overwrite.
The number that tells the story

500 script rows → 8 Sarvam API calls. Ten unique lines among the 500; one of them (...) cost nothing; the rest were absorbed by deduplication and memory. Reported cache hit rate: 64% on first run, rising toward 100% on re-runs.

Normalisation lives in exactly one place

export function normalizeForMemory(text: string): string {
  return text
    .normalize("NFC")          // visually identical Devanagari/Tamil must match
    .replace(/\r\n?/g, "\n")
    .replace(/[^\S\n]+/g, " ") // horizontal whitespace is presentation
    .replace(/ *\n */g, "\n")  // newlines are structural — kept
    .trim();
}
export function memoryHash(text: string): string {
  return createHash("sha256").update(normalizeForMemory(text), "utf8").digest("hex");
}

The hash is computed in the application rather than as a Postgres generated column, deliberately: two implementations of the same normalisation would silently drift and split the cache in two. One implementation, one source of truth.

NFC matters more than it looks. Indic scripts can compose the same visible glyph from different code point sequences; without normalisation two identical-looking lines would hash differently and both be paid for.

Human corrections outrank machines — enforced in SQL

on conflict (org_id, source_hash, source_language, target_language)
do update set
  translated_text = excluded.translated_text,
  updated_at = now()
where translation_memory.origin = 'machine'    -- ← the guard
   or excluded.origin = 'human';

A machine result can overwrite a machine entry. A machine result can never overwrite a human one. A human result can overwrite anything. This is enforced at the database level, so no application path — including a future one nobody has written yet — can violate it.

Authorisation in the database, secrets on the server.

Reviewers can correct translations but cannot alter source content — reviewing is the job of correcting machine output, but a reviewer rewriting the original script would be a different and unwanted power.

Avoiding infinite RLS recursion

create or replace function is_org_member(p_org uuid)
returns boolean language sql stable
security definer                    -- ← breaks the recursion
set search_path = public
as $$
  select exists (
    select 1 from org_members m
    where m.org_id = p_org and m.user_id = auth.uid()
  );
$$;

Without SECURITY DEFINER, the policy on org_members would query org_members through RLS, which would invoke the policy again — infinite recursion. set search_path = public is mandatory on any SECURITY DEFINER function: it prevents a caller from shadowing a table name with their own and hijacking the elevated privilege.

Secrets

  • SARVAM_API_KEY and SUPABASE_SERVICE_ROLE_KEY are server-only, validated by Zod at boot, and never prefixed NEXT_PUBLIC_.
  • Modules holding them throw at import time if window is defined — a runtime guard used instead of server-only because the standalone worker runs outside Next and must import them too.
  • .env.local is gitignored; .env.example documents the shape with no values.
  • /api/worker/tick is guarded by a shared secret rather than a session, because there is no user in that flow.

09Scale Engineering

Targets: 100+ books, 10,000+ episodes, 1,000,000+ script rows.

RequirementMechanism
1M+ script rowsbigint identity primary key; compact B-tree; append-only inserts.
Fast searchpg_trgm GIN indexes; ILIKE becomes index-backed.
Deep paginationKeyset (id > p_after), never OFFSET.
RLS at volumeorg_id denormalised; single index lookup per policy check.
Bulk writebackOne UPDATE … FROM jsonb_to_recordset per slice instead of N statements.
Queue at volumePartial index on status = 'queued' keeps the index small as finished rows accumulate.
Many reviewersOne Realtime broadcast per slice, not per row, not per client poll.
Horizontal scaleN workers; SKIP LOCKED is the only contended step.

Keyset vs OFFSET — know this cold

-- ✗ OFFSET must walk and discard every row it skips.
select * from script_rows order by id offset 900000 limit 100;

-- ✓ Keyset jumps straight into the index.
select * from script_rows where id > 900000 order by id limit 100;

At page 9,000 the first query reads 900,100 rows to return 100. The second reads 100. Keyset pagination is also stable under concurrent inserts, where OFFSET can skip or repeat rows.

The next structural step

At roughly 50M rows the answer is partitioning script_rows and translations by book_id. Nothing in the current design blocks that — queries already filter by episode or book, so partition pruning would apply immediately. Being able to name the next bottleneck, and why it is not yet worth paying for, is a strong signal in a design interview.

The 12-step smoke test

Steps 8, 9 and 12 are the important ones: they assert that something cannot happen. Negative tests are what prove a security or integrity guarantee.

11Bugs Found & Fixed

The most valuable interview material in this document. Real bugs, real diagnoses.

Why this section matters most

Interviewers use debugging stories to separate people who built something from people who followed a tutorial. Each of these has the structure they want: symptom → investigation → root cause → fix → prevention. Learn two or three well enough to tell without notes.

Bug 1 — The stage cue that got translated best story

Symptom[SFX: door creaks] came back as [SFX: கதவு கீச்சிடுகிறது. — cue translated, closing bracket destroyed.
Found byThe live-API check. Unit tests could not catch it — the fake provider echoed text back unchanged, so the structural mistake was invisible.
Root causeSpeaker splitting ran before placeholder masking. The cue contains a colon, so [SFX matched the speaker pattern and door creaks] was sent as dialogue.
FixMask the whole line first, then split the speaker — the cue becomes one opaque token with no colon. Plus a rule that character names never contain brackets.
PreventionRegression tests in both preserve.test.ts and translator.test.ts. API calls for the sample set also dropped from 6 to 4.

The lesson to articulate: mocks verify the contract you imagined; only the real dependency verifies the contract that exists. This bug lived in the ordering of two correct functions — neither was wrong alone.

Bug 2 — TypeScript interfaces silently breaking Supabase types

Symptom~60 type errors. Every query result typed as never; Property 'title' does not exist on type 'never'.
Root causeSupabase's GenericSchema requires Row extends Record<string, unknown>. TypeScript interface declarations do not get an implicit index signature; type aliases do. The schema silently failed the constraint and collapsed to never.
DiagnosisWrote a minimal probe file asserting Database["public"] extends GenericSchema, which isolated the failure in seconds instead of guessing across 60 errors.
FixConverted all 14 row shapes from interface to type. Errors: 60 → 6.

Bug 3 — Column count mismatch in a Postgres function

insert into translation_job_items (job_id, script_row_id) select sr.id from … — two target columns, one selected expression. Caught by applying migrations to a real Postgres, not by review. Fix: select v_job_id, sr.id.

Bug 4 — Untyped CASE expression

status = case when v_total = 0 then 'completed' else 'queued' end fails with "column status is of type job_status but expression is of type text". Postgres will not implicitly cast a CASE result to an enum. Fix: 'completed'::job_status on both branches. Present in two functions.

Bug 5 — The dead Translate button good UX story

SymptomUser reported "translation is not working."
InvestigationQueried the live database first rather than guessing. The job had completed: 500/500, zero failures, correct text present. The backend was healthy.
Root causeThe page defaults to English for a Hindi source book — and English was already fully translated. pendingRows === 0 rendered a greyed-out "Translate 0 rows". A finished episode looked identical to a broken one.
FixThe button now reads its state: "Translate 500 rows" / "Re-translate 500 rows" + an "All 500 rows translated" badge / "Nothing to translate".

The lesson: "not working" is a symptom, not a diagnosis. Reproducing against real data before touching code turned a suspected pipeline failure into a five-minute UI fix. Also: a disabled control with no explanation is indistinguishable from a broken one.

Bug 6 — Realtime silently delivering nothing

translation_jobs is RLS-protected and broadcast over Realtime, and the UI filters on episode_id — a non-key column. With the default replica identity, an UPDATE only writes the primary key of the old row to the WAL, so Realtime can neither evaluate RLS nor match that filter. Events never arrive; nothing errors; the progress bar sits at 0% while the job actually finishes. Fix: alter table translation_jobs replica identity full;

Bug 7 — Environment, not code

Windows Application Control blocked rollup's native .node binary (ERR_DLOPEN_FAILED). The error message blames an npm optional-dependency bug and suggests reinstalling — advice that loops forever, because the real cause is OS policy. Fix: an npm override routing rollup to @rollup/wasm-node. Worth telling as "the error message pointed at the wrong layer."

13Interview Questions — Architecture

Questions 1–8. Start every answer with the decision, then the reason.

Category A
System design & architecture
Q1
Walk me through this project in two minutes.

Vaani is a script localisation platform for comic and dubbing teams. Content is modelled as books → episodes → script rows, and a single show can reach a million rows needing translation into many languages.

Users import a script and press Translate. That doesn't translate anything — it enqueues a job in Postgres and returns immediately, because a 5,000-row episode would blow any request timeout. A background worker claims rows in slices using SKIP LOCKED, checks translation memory, sends only genuinely new lines to Sarvam AI with bounded concurrency, writes results back in one set-based statement, and updates progress — which streams to the browser over Supabase Realtime.

The hardest part was quality. Sarvam's endpoint has no system prompt, so rules like "preserve placeholders" can't be asked for — they're enforced structurally by controlling what the model sees, then verifying the output. If a placeholder doesn't survive, the row is parked rather than shipped.

The result: 500 rows translated with 8 API calls, zero failures.

Why this works: it names the problem, the key constraint, one hard technical decision, and a concrete number — in that order.
Q2
Why doesn't the Translate button translate synchronously?

Volume. An episode can hold thousands of rows, and each Sarvam call takes a few hundred milliseconds. Even with concurrency that far exceeds any HTTP or serverless timeout.

Asynchronous processing also gives three things synchronous cannot:

  • Resumability — a crash mid-job loses one slice, not the job.
  • Horizontal scale — add workers without touching the request path.
  • Progress — the user sees movement instead of a spinner.

The endpoint returns 202 Accepted with a job id, which is the honest status code for accepted-but-not-done.

Q3
Why a Postgres queue rather than Redis, SQS or RabbitMQ?

Three reasons, in order of weight:

  1. Transactional consistency. Job state and translated rows live in one database, so settling a slice and updating progress is one atomic transaction. With an external broker, a crash between "job acknowledged" and "rows written" leaves the two permanently disagreeing.
  2. SKIP LOCKED is genuinely sufficient. It gives safe multi-consumer claiming with no polling storms and no lost messages.
  3. Operational cost. No second system to deploy, secure, monitor and back up.

I'd move to a dedicated broker at very high throughput — tens of thousands of jobs per second, where queue traffic starts competing with application queries for database resources — or if I needed fan-out to multiple independent consumer groups. Neither applies here.

Strong close: naming the condition under which you'd change your mind shows judgement rather than dogma.
Q4
How would you add a second translation provider?

One new class satisfying TranslationProvider — four members: name, model, maxInputChars, and the supports() / translate() pair — plus one line in the registry. No caller changes.

Registration order is preference order, so Sarvam stays first and keeps Indic pairs going to the specialist model; anything it doesn't support falls through. maxInputChars means chunking adapts automatically, and supports() lets the router reject an unsupported pair up front with a clear error rather than discovering it through a 400 deep inside a batch.

Q5
Why is the translation service framework-free?

Nothing under services/translation/ imports Next.js, and the database is reached through a MemoryPort interface rather than a Supabase client.

The practical payoff is testing: the entire pipeline runs against an in-memory fake with no database and no network, which is why 44 tests execute in under a second. The secondary payoff is that the domain logic would survive a framework change untouched. The worker already proves the point — it runs outside Next entirely and imports the same modules.

Q6
Where does business logic live — application or database?

Split deliberately:

  • Database: anything that must hold regardless of which code path runs — org scoping (RLS), "one live job per episode/language" (partial unique index), "machine never overwrites human" (guarded upsert), atomic claim and roll-up.
  • Application: anything needing rich logic or external calls — text protection, chunking, provider routing, retry policy, batching.

The test is: could a future code path violate this? If yes, it belongs in the database as a constraint. Invariants in application code are conventions; invariants in the database are guarantees.

Q7
How does the system handle a worker crashing mid-job?

Claimed items sit in running with a locked_at timestamp. On the next tick, requeue_stuck_job_items() finds anything locked more than ten minutes and either returns it to queued or — if it has burned its attempt budget — parks it as failed with "abandoned by worker".

So a crash costs at most one slice and at most ten minutes. Other workers keep draining the rest of the job the whole time, because claiming is per-slice, not per-job.

Q8
What was the hardest technical decision?

Failing loudly on placeholder loss. When a sentinel doesn't survive translation the pipeline retries with a different shape, and if that fails it throws — the row is parked instead of shipped.

That's deliberately choosing lower completion over higher risk. The alternative — return slightly-wrong text — is worse at this scale: a flagged row is visible and fixable in the review queue, while silent corruption spread across a million rows might not surface until it's in a dubbing studio. Correctness beat completeness because the failure was silent and the blast radius was large.

Pattern: name the trade-off, name the alternative, then justify with the cost of being wrong.

14Interview Questions — Database

Questions 9–20. The deepest technical section; expect the most probing here.

Category B
PostgreSQL, indexing & data modelling
Q9
Explain FOR UPDATE SKIP LOCKED.

FOR UPDATE takes a row-level write lock. Normally a second transaction wanting the same row blocks until the first commits. SKIP LOCKED changes that: skip any locked row and move to the next unlocked one.

That's exactly what a queue needs. Ten workers each ask for 100 queued items and each gets a disjoint 100 with no waiting. Without it they'd all target the same rows by id order and serialise into a single-consumer queue with extra steps.

The claim is a CTE: select candidate ids with SKIP LOCKED, update those to running while incrementing attempts, and return them joined to the script rows — all in one atomic statement.

Q10
Why bigint for script_rows but uuid for books?

Access pattern and volume. script_rows is the million-row table, always read in row_index order within an episode, and referenced by a foreign key from every translation row. A bigint is 8 bytes and sequential; a uuid is 16 and random.

Sequential keys mean inserts append to the right edge of the B-tree instead of scattering writes across it, which keeps the index dense and cache-friendly. Doubling the key width also doubles it in every index and every referencing foreign key.

Books are few, created rarely, and their ids appear in URLs — where uuids are preferable because they don't leak how many books exist or allow enumeration.

Bonus: if you want both, UUIDv7 is time-ordered and gives sequential locality with uuid opacity.
Q11
Why denormalise org_id when you could join?

Because RLS runs on every row of every query. Deriving the org through script_rows → episodes → books would make each policy check a two-level join, multiplied by every row scanned.

Storing org_id directly makes the predicate a single indexed lookup. The cost is a redundant uuid per row and the obligation to keep it consistent — handled by setting it at insert and cascading deletes from the organisation. That's a good trade when the alternative is paying a join on the hottest path in the system.

Q12
What is a partial index and why use one here?

An index with a WHERE clause — it only contains rows matching that predicate.

The claim query only ever looks at status = 'queued'. Once a million items have been processed, a full index would carry a million mostly-irrelevant entries; the partial index holds only what's actually queued, staying small and cache-resident no matter how much history accumulates.

The other one is a correctness constraint: a unique partial index on (episode_id, target_language) where status in ('queued','running') makes duplicate live jobs impossible at the database level, even under a race.

Q13
How does search stay fast on a million rows?

A GIN index using pg_trgm. Trigram indexing breaks text into three-character sequences, which lets Postgres serve ILIKE '%query%' from the index.

A B-tree can't help with a leading wildcard — it can only seek a known prefix. Full-text search is the other option, but tsvector does stemmed whole-word matching; it wouldn't find a partial character name or a fragment mid-word, which is what reviewers actually search for.

The trade-off is a larger index and slower writes — acceptable for content written once and searched constantly.

Q14
Explain keyset pagination and why you chose it.

Instead of OFFSET 900000 LIMIT 100, the query says WHERE id > 900000 ORDER BY id LIMIT 100.

OFFSET must read and discard every skipped row — page 9,000 reads 900,100 rows to return 100, so it degrades linearly with depth. Keyset seeks directly into the index and reads exactly 100 regardless of depth.

It's also stable under concurrent writes: with OFFSET, a row inserted earlier in the ordering shifts everything, so a user paging forward can see a row twice or miss one entirely. Keyset is anchored to a value, not a position.

The cost is losing random access to page N — acceptable, since nobody jumps to page 9,000 of a script.

Q15
How does RLS work here, and how did you avoid infinite recursion?

Every table has policies calling is_org_member(org_id) or has_org_role(org_id, roles[]), which check the current user via auth.uid() against org_members.

The recursion problem: the policy on org_members needs to query org_members, which triggers the policy again, forever. The fix is SECURITY DEFINER — the helper runs as its owner and bypasses RLS for that lookup.

Critically, SECURITY DEFINER functions must set search_path = public. Otherwise a caller could create a table shadowing org_members in a schema earlier in their path and hijack the elevated privilege. That's a well-known Postgres privilege escalation vector.

This answer scores highly: naming the search_path attack shows security depth beyond "I enabled RLS."
Q16
How do you write 100 translation results efficiently?

One statement: UPDATE … FROM jsonb_to_recordset(p_results). The worker sends the whole slice as a JSON array, Postgres expands it into a relation, and the update joins against it.

A hundred individual updates would be a hundred round trips plus a hundred transactions. At a million rows that's the difference between minutes and hours.

The same statement carries a guard — and t.status in ('pending','failed','machine') — so a reviewer who edited a row while the job was in flight is never overwritten.

Q17
Why compute the memory hash in the app rather than a generated column?

A generated column was the first instinct, and it would guarantee the hash is always present. But it would mean the normalisation logic existing twice — once in TypeScript for lookups, once in SQL for storage.

Those two would drift. The moment they disagree on, say, Unicode NFC or whitespace collapsing, the cache silently splits in two: lookups miss, entries duplicate, and nothing errors. Since a cache miss just costs money rather than breaking anything, the failure would be invisible for a long time.

One implementation, one source of truth, documented in the migration so nobody writes that table by raw SQL.

Q18
How do you guarantee a machine translation never overwrites a human correction?

Two independent guards, both in SQL:

  • Translation memory: the upsert's DO UPDATE carries WHERE translation_memory.origin = 'machine' OR excluded.origin = 'human'.
  • Translation rows: the bulk writeback only touches status IN ('pending','failed','machine') — edited and approved are excluded.

Both are in the database, not the application, so no code path — including one written next year by someone else — can violate them. The smoke test asserts both explicitly, because a guarantee that isn't tested is a hope.

Q19
What is REPLICA IDENTITY FULL and why did you need it?

It controls how much of the old row Postgres writes to the WAL on UPDATE and DELETE. The default writes only the primary key.

That broke Realtime here for two reasons: the subscription filters on episode_id, which isn't the primary key and so isn't in the WAL record; and because the table is RLS-protected, Realtime needs the full row to evaluate whether each subscriber may see it.

The symptom was nasty — no error anywhere, just a progress bar frozen at 0% while the job completed normally. Setting REPLICA IDENTITY FULL writes the whole old row. The cost is a larger WAL record per update, negligible here because the table is updated once per slice, not per row.

Q20
How would you scale past a million rows?

The current design should hold comfortably at a million; the indexes and access patterns are already sized for it. The next structural step, around 50M, is partitioning script_rows and translations by book_id.

That works cleanly because queries already filter by episode or book, so partition pruning applies immediately, and dropping a finished show becomes a partition drop instead of a mass delete.

Before that I'd add read replicas for the review UI — reviewers are read-heavy and the worker is write-heavy, so they separate naturally. I wouldn't do either preemptively; both add operational complexity that isn't yet earned.

15Interview Questions — Queue & Concurrency

Questions 21–28.

Category C
Background jobs, concurrency & reliability
Q21
What happens if two users click Translate simultaneously?

One job. enqueue_translation_job() first looks for a live job for that (episode, language) and returns its id if found. If both requests pass that check simultaneously, the partial unique index on (episode_id, target_language) where status in ('queued','running') makes the second insert fail.

The application check handles the common case efficiently; the index handles the race correctly. Relying on the check alone would be a TOCTOU bug.

Q22
How do you prevent double-charging for the same translation?

Four mechanisms compounding:

  1. Only rows that need work are enqueued — already-translated rows are skipped entirely.
  2. Identical rows within a slice collapse to one call before anything is sent.
  3. Translation memory is consulted before any API call.
  4. Idempotent enqueue means a double click can't create a second job.

Measured: 500 rows, 8 calls.

Q23
Why bounded concurrency instead of Promise.all?

Promise.all over a 100-row slice fires 100 simultaneous HTTP requests. That immediately trips rate limits, and rate-limit responses cost real money in retries and latency while accomplishing nothing.

mapWithConcurrency keeps a fixed number in flight — default 8, configurable — by running N workers over a shared cursor. Results stay in input order regardless of completion order. The right number is whatever the provider's rate limit allows, which is why it's an environment variable rather than a constant.

Q24
Explain your retry strategy.

Retryability is a property of the error, not the operation:

  • 429, 5xx, timeouts, network errors — transient. Retried with exponential backoff and full jitter, honouring Retry-After when the server sends it.
  • 4xx — the request is malformed and will stay malformed. Retrying burns quota for a guaranteed failure.

That's why TranslationError carries a retryable flag — the decision is made where the error is understood, not guessed at by the caller. Above that sits a second layer: a row that keeps failing gets requeued up to maxAttempts, then parked as failed for a human.

Q25
Why full jitter rather than plain exponential backoff?

With plain backoff every client that failed at the same moment waits the same interval and retries in the same instant — the thundering herd re-forms at each attempt.

Full jitter picks uniformly between 0 and the ceiling, spreading retries across the window. With 8 concurrent workers all hitting one rate limit simultaneously, this is the difference between a smooth recovery and eight synchronised waves.

Q26
How does progress reach the browser?

Supabase Realtime over postgres_changes, filtered to the episode. The worker calls mark_job_items(), which settles the slice and recomputes counters in the same transaction, producing exactly one UPDATE on translation_jobs. Realtime broadcasts that to every subscriber.

One broadcast per slice rather than per row — 5 events for a 500-row job instead of 500 — and because counters are recomputed transactionally, every event carries a consistent snapshot rather than a torn one. Polling would have cost more than the translation.

Q27
Can you run multiple workers? What breaks?

Yes, and nothing breaks. SKIP LOCKED means each worker takes a disjoint slice. Nothing else in the pipeline is contended: memory lookups are reads, writebacks are keyed by row, and counter roll-ups are recomputed from the items table rather than incremented, so they're order-independent.

The real limit is the Sarvam rate limit, not the database. Total concurrency is workers × TRANSLATION_CONCURRENCY, so both are configurable.

Q28
Why recompute counters instead of incrementing them?

Incrementing (completed_rows = completed_rows + N) is order-dependent and drifts. A retried slice, a double-settle after a crash, or two workers finishing simultaneously can all produce a wrong total that never self-corrects.

Recomputing with aggregate COUNT(*) FILTER (WHERE …) over the items table is idempotent: it derives truth from the queue's actual state, so running it twice gives the same answer and any drift heals on the next slice. Slightly more expensive, and correct by construction.

16Interview Questions — API Integration & Resilience

Questions 29–36.

Category D
External APIs, failure handling & cost
Q29
How do you handle an API with no batch endpoint?

Sarvam's /translate takes one input per call — there's no multi-input form. So throughput comes from reducing calls and parallelising what remains, not from packing payloads.

Reduce: skip untranslatable lines, dedupe identical rows, hit translation memory. Parallelise: bounded concurrency over whatever survives. That's how 500 rows became 8 calls — the batching is logical, not protocol-level.

Q30
How do you handle input longer than the API limit?

chunkText() splits with a preference cascade: sentence boundaries first — including the Devanagari danda । and double danda ॥, not just Latin punctuation — then clause boundaries, then whitespace, and only as a last resort mid-word.

The limit comes from provider.maxInputChars, so it adapts per provider and per model (2,000 for sarvam-translate:v1, 1,000 for mayura:v1) rather than being hardcoded. Chunks are rejoined at sentence boundaries, so a single space reassembles them cleanly even if the model trims its own output.

Detail worth mentioning: handling the danda shows you thought about the actual languages, not just ASCII.
Q31
How do you test code that calls a paid external API?

Three layers, because each catches what the others can't:

  • Unit tests with a fake provider — fast, free, deterministic. Covers pipeline logic and failure isolation.
  • Injected fetch — the Sarvam provider accepts a fetchImpl, so request shape, retry behaviour, 429 handling and error mapping are all tested against stubbed HTTP responses with no network.
  • A live check (npm run check:sarvam) — a handful of representative lines against the real API, run deliberately rather than in CI.

That third layer earned its place: it caught the stage-cue bug that both other layers passed, because the fake provider echoed text back unchanged and the structural mistake was invisible.

Q32
The API is non-deterministic. How do you build reliably on it?

Assume any single call may misbehave, and verify rather than trust. Placeholders are checked on return; if a sentinel is missing the line is retried with a different sentinel shape, and only after both fail is the row parked.

I actually measured this: the same input occasionally lost a #0# that survived a moment earlier. Rather than assume the sentinel was bad, I probed eight shapes across four languages and confirmed #0# is fine — the variance was model non-determinism. So the two-shape retry stays, converting a random failure into a second attempt.

Strong signal: "I measured it" beats "I assumed it" in every interview.
Q33
How do you keep API keys safe?

Server-only, always. Never prefixed NEXT_PUBLIC_, since that prefix is what tells Next.js to inline a value into the client bundle. Validated by Zod at boot so a missing key fails immediately with a clear message rather than at the first translation.

Modules holding secrets throw at import time if window is defined. I used a runtime guard rather than the server-only package because the standalone worker runs outside Next and has to import the same modules — server-only relies on a bundler condition that isn't present there.

Q34
A user says translations are slow. How do you debug it?

Work down the stack, measuring at each layer rather than guessing:

  1. Is the worker running? The single most common cause — a queued job with no consumer looks identical to a slow one.
  2. Job counters — is completed_rows moving? That separates "stuck" from "slow".
  3. Cache hit rate — tm_hits versus total. A cold cache on unique content is expected to be slow.
  4. Provider latency — the provider records latencyMs per call; rising latency or 429s means back off concurrency.
  5. Database — EXPLAIN ANALYZE the claim query; check the partial index is being used.

The instrumentation exists for exactly this: every slice logs done, failed, requeued, from-memory and API calls.

Q35
How would you add cost tracking?

Most of it is already there: translation_memory.use_count counts calls avoided, and each job records tm_hits. The /memory page surfaces both.

To complete it I'd log per-call character counts and latency into a translation_usage table keyed by org and day, then compute spend against the provider's rate. That enables per-org budgets and quota alerts — the natural next step for a multi-tenant product where one team's re-translation shouldn't exhaust everyone's quota.

Q36
What if Sarvam goes down entirely?

Today: 5xx responses are retried with backoff; rows exhausting their attempt budget park as failed and stay visible in the review queue. Nothing is lost — the queue holds and re-running picks up exactly the failed rows.

What I'd add: a circuit breaker. After N consecutive failures, stop calling for a cooldown instead of grinding every row through its full retry budget against a dead service. The provider abstraction also makes failover viable — register a fallback and have the router try it when the primary is open-circuit.

17Interview Questions — Domain & Translation Quality

Questions 37–43. This is where the project stops looking generic.

Category E
The localisation problem itself
Q37
How do you stop the model translating character names?

The name never reaches the model. Two paths: a dedicated character_name column, which is simply never sent; and inline prefixes like Raju: Namaste sabhi ko., where splitLine() separates marker | speaker | body | trailing and only the body is translated. The speaker is reattached verbatim afterwards.

Speaker detection is deliberately conservative — max four words, no sentence-ending punctuation, no brackets — so ordinary prose like "He said the only thing that mattered: nothing." isn't mistaken for dialogue. The episode's known character names are also passed in, so matching is exact rather than heuristic where possible.

Q38
How do you protect placeholders through translation?

Mask, translate, verify, restore.

Nine regex patterns cover {{x}}, {x}, [[x]], [SFX: …], HTML tags, %s, %1$s, ${x} and $SHOUTY_VAR, ordered longest-construct-first so {{name}} matches before {name}. Each becomes a sentinel; the model sees only sentinels.

The verification step is what makes it trustworthy rather than hopeful: if any sentinel is missing on return, retry with a different shape, then fail the row rather than restore into text that has lost its markers.

Q39
Why not just prompt an LLM with the rules?

Two reasons. First, Sarvam's translate endpoint has no system prompt — there's literally no channel to send instructions through. The constraint forced the structural approach.

Second, it's better anyway. A prompt is a request the model may ignore, especially on long or unusual inputs; masking is a guarantee, because the protected content is physically absent from what the model sees. If I added an LLM provider I'd use prompting as well — but I'd keep the structural layer underneath, since it's the one that can be verified.

This is a standout answer — it reframes a limitation as a design insight.
Q40
Why only 23 languages when the spec asked for Spanish, Japanese and others?

Because Sarvam's translate endpoint covers English and the 22 scheduled Indian languages and nothing else. I verified that against the API documentation before writing code, and raised it rather than discovering it in production.

Listing languages that would fail at runtime would be worse than being honest: the supported set lives in one file, and the UI only offers what genuinely works. The provider abstraction exists precisely so a second provider can widen it — that's a one-file change.

Shows: you validate requirements against reality and communicate constraints early — a professional trait interviewers actively look for.
Q41
How does the review loop improve quality over time?

A reviewer edits a translation; save_translation_correction() updates the row to edited or approved and writes the corrected wording into translation memory with origin = 'human' — in one transaction.

The next time that source line appears anywhere in the catalogue, the corrected version is reused instead of re-asking the model. Because the database blocks machine output from overwriting human entries, the improvement is permanent. Review effort compounds instead of evaporating — which is the difference between a translation tool and a translation system.

Q42
How do you handle right-to-left languages?

Urdu, Kashmiri and Sindhi use Perso-Arabic script. The language table records the script, and isRtl() drives a dir="rtl" attribute on both the display cell and the edit textarea, so the browser handles bidirectional layout and cursor behaviour natively.

Font stacks also include Noto families for Devanagari, Tamil and Bengali, because default system fonts often render Indic scripts with broken conjuncts.

Q43
What quality checks would you add next?

Automated signals that flag suspicious output for human attention without blocking the pipeline:

  • Length ratio — output far longer or shorter than expected for the pair usually means truncation or hallucination.
  • Script detection — untranslated Latin text sitting in a Tamil target means the model passed it through.
  • Glossary compliance — once a term base exists, verify enforced terms actually appear.
  • Back-translation sampling — translate a random sample back and compare, as a cheap regression signal when changing models.

These are warnings, not gates — the existing hard failure is reserved for placeholder loss, where the output is definitively broken.

18Interview Questions — Frontend & Next.js

Questions 44–50.

Category F
React, Next.js App Router & UX
Q44
Server Components vs Client Components — how did you decide?

Default to server; opt into client only where interactivity demands it. Pages are Server Components that query Supabase directly — no API layer, no loading state, no data serialisation beyond what React already does.

Client Components are the four that need browser state: the translate panel (Realtime subscription, fetch), the review table (inline editing), the search bar, and the forms. Each is a leaf, so the interactive JavaScript shipped stays small.

Q45
Why does /api/translate exist when Server Actions could do it?

Both exist, deliberately. Server Actions handle form submissions where a full round trip and revalidation are natural — creating a book, importing a script.

The translate flow is different: the client needs the job id back to subscribe to Realtime, and it shouldn't navigate or re-render the page. A Route Handler returning 202 with the job is the honest shape for that. Route Handlers are also callable by things that aren't the app — which matters for the worker tick endpoint.

Q46
How does the Realtime subscription work, and how do you avoid leaks?

A useEffect opens a channel subscribed to postgres_changes on translation_jobs, filtered server-side by episode_id so the socket stays quiet in a workspace running many jobs.

The effect returns a cleanup that calls removeChannel, and its dependency array is episode, language and router — so switching language tears down the old channel and opens a new one. The browser client itself is memoised at module level, because each instance would open its own socket.

When the job reaches a terminal state the component also triggers router.refresh() to pull the freshly translated rows in.

Q47
How do you handle optimistic updates in the review editor?

Editing keeps a local override map keyed by translation id. On save, the PATCH fires and on success the override is applied immediately with the new status — so the row updates without a full page refetch, which matters when you're working down a list of a hundred corrections.

On failure the error is stored per row and shown inline, leaving the edit in place so the work isn't lost. I deliberately didn't apply the change before the request resolved: a correction that silently failed to save would be worse than a brief wait.

Q48
How does authentication work across server and client?

Supabase Auth with cookie-based sessions via @supabase/ssr. Middleware refreshes the session on every request and gates unauthenticated users to /login.

The middleware is load-bearing, not decorative: Server Components cannot set cookies, so without it the refreshed token would have nowhere to go and sessions would silently expire mid-visit. Three clients exist for three contexts — browser, server-with-session, and service-role for the worker.

Q49
A user reports "translation is not working." How do you respond?

This actually happened. I checked the data before touching code: queried the jobs table, found the job had completed — 500/500, zero failures — and confirmed the translated text was present and correct. The backend was healthy.

Then I reproduced what the user's page would render, and found it: the episode defaults to English for a Hindi source book, English was already fully translated, so pendingRows was 0 and my button rendered greyed out as "Translate 0 rows". A finished episode looked exactly like a broken one.

Fixed by making the button state legible — "Re-translate 500 rows" plus an "All 500 rows translated" badge. The lesson: "not working" is a symptom, and reproducing against real data turned a suspected pipeline failure into a five-minute UI fix.

Use this one. It demonstrates debugging discipline and owning a UX mistake — both rare and valued.
Q50
How do you render a hundred-thousand-row episode?

You don't. The page is keyset-paginated at 100 rows with a server-side search across source text, character names and translations — so a reviewer finds the rows they need instead of scrolling to them.

If a continuous view were required I'd add windowing with react-window so DOM nodes stay proportional to the viewport, not the dataset. I'd avoid that until asked, though — virtualisation complicates find-in-page, accessibility and text selection, and search solves the real user need more simply.

19Interview Questions — Security

Questions 51–56.

Category G
Security & multi-tenancy
Q51
How do you guarantee tenant isolation?

RLS on all ten tables, with policies checking org membership through is_org_member() / has_org_role(). Authorisation lives in the database, not in application code.

That's the important part: even if an API route forgot a WHERE org_id = …, the database returns nothing. Application-layer authorisation is one forgotten filter away from a cross-tenant leak; RLS makes the safe path the default. The smoke test asserts it negatively — a viewer attempting to start a job gets insufficient_privilege.

Q52
The worker bypasses RLS. Isn't that dangerous?

It's a real risk, managed deliberately. The worker has no user session — it processes rows on behalf of many tenants — so it uses the service role.

Containment:

  • Exactly one module creates that client, documented as worker-only.
  • It's never imported into a request path; user-facing code uses the session client.
  • The RPCs it calls still scope by org_id explicitly.
  • The key is server-only, guarded against browser import.

The rule I'd state in review: never reach for the service role to "fix" a permissions problem in a user-facing path — that path should be using the session client.

Q53
Why is set search_path on SECURITY DEFINER functions non-negotiable?

A SECURITY DEFINER function runs with its owner's privileges. Without a pinned search_path, it resolves unqualified table names using the caller's path.

An attacker who can create objects could define their own org_members in a schema earlier in that path, and the elevated function would read their table instead of the real one — returning whatever membership they choose. Pinning search_path = public closes it. It's a documented Postgres privilege-escalation vector, not a theoretical one.

Q54
How is the worker endpoint protected without a user session?

A shared secret in the x-worker-secret header, compared against WORKER_TICK_SECRET. Session auth is meaningless there — the caller is a cron scheduler, not a person — and the route is excluded from the auth middleware for that reason.

Improvements for production: constant-time comparison to avoid timing leaks, secret rotation, and IP allowlisting where the scheduler has stable egress.

Q55
What's the difference between the anon key and the service role key?

The anon key is a public identifier safe to ship to browsers — everything it can reach is bounded by RLS, so it grants nothing on its own. The service role key bypasses RLS entirely: full read/write across every tenant.

So they get completely different handling. Anon is NEXT_PUBLIC_; service role never is, lives only in server environment, and is treated as compromised the moment it appears anywhere it shouldn't — in which case the correct response is rotation, not hoping.

Q56
What security issues remain?

Being straightforward about this is better than claiming none:

  • No rate limiting on the translate endpoint — a malicious editor could queue expensive jobs repeatedly. Needs per-org quotas.
  • No audit log — who approved what, and when, isn't recorded. Real localisation workflows need that for accountability.
  • Worker secret comparison isn't constant-time.
  • No CSRF hardening beyond SameSite cookies — adequate for now, worth revisiting.
  • Imported script content isn't scanned — it's rendered as text, not HTML, so injection risk is low, but export paths would need care.

20Interview Questions — Behavioural

Questions 57–62. Same rigour, told as narrative.

Category H
Behavioural & storytelling
Q57
Tell me about a difficult bug you debugged.

Situation: Testing the pipeline against the live API, a stage cue [SFX: door creaks] came back as [SFX: கதவு கீச்சிடுகிறது. — translated, with the closing bracket gone. My unit tests all passed.

Investigation: The tests used a fake provider that echoed text back, so a structural mistake was invisible — the text went out and came back looking fine. I traced what was actually sent and found the payload was door creaks], not the whole cue.

Root cause: Speaker-splitting ran before placeholder masking. The cue contains a colon, so [SFX matched the speaker pattern and the rest was treated as dialogue. Neither function was wrong alone — the ordering was.

Fix: Mask the whole line first, then split the speaker, so the cue is one opaque token with no colon. Plus a rule that character names never contain brackets. Added regression tests at both layers. API calls for the sample set also dropped from 6 to 4.

Lesson: mocks verify the contract you imagined; only the real dependency verifies the one that exists.

Q58
Tell me about a time you disagreed with a requirement.

The spec listed sixteen target languages including Spanish, French, Japanese and Chinese, and named Sarvam as the provider. Checking Sarvam's documentation first, I found it covers English and the 22 scheduled Indian languages only — fourteen of the sixteen were unreachable.

I raised it immediately with the evidence and options: route non-Indic languages to a second provider, or trim the list to what genuinely works. The decision was to trim, so I built the supported set as a single source of truth with the UI offering only real languages — and kept the provider abstraction so widening it later is one file.

Lesson: validating requirements against the actual API before writing code turned a guaranteed production failure into a five-minute conversation.

Q59
Tell me about a mistake you made.

I shipped a Translate button that rendered greyed out reading "Translate 0 rows" whenever an episode was already fully translated — with no explanation and no way to re-run. A user reported "translation is not working," and they were right to.

The backend was fine; I'd simply never designed a state for "already done", so success and failure looked identical. I'd validated the pipeline exhaustively and under-tested the interface around it.

Fixed by making the state legible — "Re-translate 500 rows" with a confirmation badge, and distinct copy for "no rows imported yet". The broader lesson: a disabled control with no explanation is indistinguishable from a broken one, and I now treat empty and completed states as first-class rather than afterthoughts.

Q60
How did you decide what to test?

By cost of being wrong, not by coverage percentage. Tests concentrate where a silent failure would be expensive and hard to detect: the placeholder round-trip, speaker splitting, chunking, provider routing, batch deduplication, memory hits and failure isolation.

The most valuable tests are the negative ones — asserting that a machine translation cannot overwrite a human correction, and that a viewer cannot start a job. Those prove a guarantee rather than a behaviour.

I didn't unit-test the CSS or trivial getters. I did spin up a real Postgres to validate migrations, which caught two bugs no amount of review would have.

Q61
What would you do differently starting over?
  • Test against the real API sooner. The stage-cue bug existed for a while behind passing tests. I'd run a live check on day one.
  • Generate database types from the start rather than hand-maintaining them — that cost an hour of confusing never errors.
  • Design empty and completed states alongside the happy path, given the dead-button bug.
  • Consider segment-level translation memory earlier. Row-level was simpler and matched the spec, but segment-level would meaningfully raise hit rates and is harder to retrofit.

What I'd keep: the provider abstraction, the Postgres queue, and enforcing invariants in the database. All three paid off repeatedly.

Q62
What are you most proud of here?

That the quality guarantees are real rather than aspirational. It would have been easy to send each row to the API, store what came back, and call it done — it would demo fine.

Instead the pipeline provably preserves character names, placeholders, stage cues, line breaks and numbering, and refuses to ship a row it can't verify. That's backed by tests, by a live-API check, and by a real bug it caught.

The 500-rows-for-8-API-calls number is the same story from the commercial side: the design isn't just correct, it's economically viable at the scale it targets.

The five sentences that matter

  1. "Translate doesn't translate — it enqueues." Async because a 5,000-row episode outlives any request timeout.
  2. "The rules are structural, not prompted." No system prompt exists, so the model never sees protected content — and output is verified, not trusted.
  3. "The queue is Postgres, using SKIP LOCKED." Transactional consistency with the data, no second broker.
  4. "Invariants live in the database." Machine can never overwrite human; one live job per episode/language. Constraints, not conventions.
  5. "500 rows cost 8 API calls." Skip untranslatable → dedupe → memory → human corrections persist.

Concepts to be able to explain cold

  • FOR UPDATE SKIP LOCKED
  • Keyset vs OFFSET pagination
  • Partial indexes (perf and correctness)
  • Trigram GIN vs B-tree vs tsvector
  • RLS + SECURITY DEFINER + search_path
  • REPLICA IDENTITY FULL and Realtime
  • Exponential backoff with full jitter
  • Idempotency (enqueue, counter roll-up)
  • Bounded concurrency vs Promise.all
  • interface vs type index signatures
